# SAP BTP solution architecture for clients

Use this skill when a user asks for an SAP BTP architecture design, review, explanation, or interactive architecture page. Produce a **project-specific, navigable HTML file with an actual architecture diagram** that a non-technical client can use to understand what each included service does and why it is in this solution. Respond to the user in their language; the HTML itself must support Portuguese (Portugal), English, Spanish, and French.

An attached architecture HTML or diagram is a **visual and interaction reference**, not evidence that its services, account counts, editions, tenants, or connections belong to the current project. Preserve useful layout patterns (global account, directories, subaccounts, clickable service details, environment filters, print view), but regenerate its content from confirmed project facts. Do not copy illustrative numbers or topology into a new client's architecture.

Use the [SAP solution diagram introduction](https://sap.github.io/btp-solution-diagrams/docs/solution_diagr_intro/big_picture/) and the [official editable examples, shapes and SVG assets](https://github.com/SAP/btp-solution-diagrams/tree/main) as the visual source: clean SAP/Fiori Horizon shapes, nested BTP boundaries, separate customer-network zones, official SAP service icons, and **real directional connectors**. These references describe high-level diagrams for different audiences; choose readable L0/L1 detail for a client. Do not claim that a custom output is an SAP-certified diagram or copy someone else's product inventory.

**Presentation versus diagram:** The page header must display the exact title `CGUTECH - SAP Business Technology Platform Solution Architecture`, identical to the HTML `<title>` and `document.title` (see section 5). Use Cgutech's current website palette in the HTML presentation chrome (navy `#232D4B`, magenta `#E20074`, yellow `#F5F340`) for the masthead, navigation states, accents, and focus treatment. Keep the actual SAP architecture diagram's approved light-blue/white boxes, blue borders, and grey-blue connectors **unchanged**; do not recolor the diagram to Cgutech brand colors. Keep brand resources embedded/offline or use a text wordmark; never require a remote font or logo.

**Delivery order:** create a real, editable `.drawio` architecture file **first**; validate its structure and SAP styling; then generate the self-contained HTML from the same component, placement, icon and edge inventory, rather than producing an unrelated redrawing. Keep both files available to the user. If one overview cannot fit without overlaps or tiny text, use multiple named draw.io pages (for example solution landscape and connectivity) and corresponding views in the HTML.

Use the official SAP BTP service SVG for every confirmed SAP service with an exact match in the SAP repository; map product name and edition to the correct asset and use the diagram variant with the grey circular background. Put that icon **immediately next to its full service name inside every subaccount where the service is present**, in both the editable diagram and **every HTML view, including the overview**. An unlabeled row of icons, icons that reveal names only on hover, and a separate service legend do not satisfy this requirement. In dense overviews, reflow or stack the subaccounts and named service rows instead of shrinking the labels or hiding them; keep the focused views too. Embed or package assets so both outputs are portable/offline. If no exact official icon exists (for example a PostgreSQL service without a matching published icon), use a clearly neutral generic symbol next to the service name and do not substitute another product's icon or claim it is official. Respect the asset repository's license and attribution requirements when distributing copies.

## 1. Discover the actual solution before drawing it

**Ask first, draw second.** Confirm which services are in scope, even if an image or earlier example is supplied. Do not turn suggested services, icons, or available capabilities into deployed components. Ask focused questions one at a time, reusing answers already provided. If the user wants a preliminary design without all answers, include only known components and flows; omit unknown technical attributes rather than inventing them. Do not add pending-decision labels, sections, or commercial inventory references unless explicitly requested.

Gather, as applicable:

1. **Purpose and audience:** What business process, application, or integration is being described? Is the deliverable a proposed design or an as-built inventory? Who will read it? Is there a customer/project name and a preferred starting language?
2. **BTP organization:** Which global account, directories, subaccounts, environments (DEV, TST/QAS, PRD, others), regions, and infrastructure providers exist or are planned? Which environments share a subaccount and which require isolation? Are region or data-residency requirements defined?
3. **Actual service scope:** Which services, editions and capabilities are planned in each subaccount? When relevant, check SAP Integration Suite and its capabilities, SAP Business Data Cloud / SAP Datasphere / SAP Analytics Cloud, Cloud Foundry runtime, PostgreSQL, SAP Build Work Zone, SAP Build Process Automation, SAP Business Application Studio, Audit Log, Cloud Logging, Job Scheduling, CI/CD, and Cloud Transport Management. Do not assume that a runtime, SaaS tenant, or shared service is instantiated separately in every subaccount.
4. **SAP source and target systems:** Identify the client's actual ERP: SAP ECC, SAP S/4HANA Private Cloud, or SAP S/4HANA Public Cloud. For each, confirm DEV, QAS/TST, and PRD landscapes, network location, target systems, and actual communication directions. Do not equate BTP and SAP environments by name without confirmation. Make the ERP and its confirmed BTP connections unmissable in both the editable diagram and HTML, with an ERP node for each confirmed target environment; never leave the ERP only in explanatory text.
5. **Connectivity and data flow:** Which flows exist between which exact endpoints? Record direction, initiator, purpose, protocol (HTTPS, OData, RFC, SOAP, events, etc.), authentication, sensitivity, and any private networking or proxy requirements. For this architecture convention, BTP-to-ECC or BTP-to-S/4HANA Private Cloud private access must run via SAP Cloud Connector; verify that the proposed direction can use it and draw its node and links. Do not apply this requirement to S/4HANA Public Cloud: draw the actual approved cloud connection without inserting Cloud Connector merely because it is SAP ERP. Include Destination/Connectivity only when actually used. If a direction is not known or is incompatible with Cloud Connector, ask rather than invent a flow.
6. **Identity:** Which corporate IdP (for example Microsoft Entra ID), SAP Cloud Identity Services components (Identity Authentication/IAS, Identity Provisioning/IPS, Identity Directory), tenants, trusts, SAML/OIDC arrangements, provisioning connectors, and SCIM scopes are in scope? Federation and provisioning are separate flows. Show the shared IAS as the central authentication and identity source for all affected BTP directories/subaccounts; distinguish that role from effective permissions applied by BTP role collections and applications.
7. **Delivery and operations:** How are build, deployment, and promotion performed? Where do CI/CD and Cloud Transport Management live? Which content types are actually transported? Ask about monitoring, audit/retention, backup/recovery, availability, segregation of duties, and compliance only when relevant to the requested design.

When SAP Cloud Transport Management is used, **draw promotion edges between the actual source and destination subaccounts in every confirmed domain**, with the shared service as the central transport orchestrator. Do not equate central placement with Application-only scope. In the confirmed example, show Application `DEV -> TST -> PRD`, Data `DEV/TST -> PRD`, and Integration `DEV/TST -> PRD`, and identify the central cTMS in Shared Services. Do **not** invent a separate TST account or a DEV-to-TST edge for the shared Data/Integration subaccounts, or a promotion path within the single Shared Services account. Make the central service's cross-directory scope explicit in the diagram and service details. Confirm supported content types and the transport setup separately; do not claim that every service's artifacts can be transported.

**Group product capabilities in both outputs.** SAP Business Data Cloud is the enclosing offering for the included SAP Datasphere and SAP Analytics Cloud capabilities: show them visibly nested inside its boundary, not as three unrelated peers or three separately instantiated services. SAP Integration Suite encloses its included capabilities: Cloud Integration, API Management, and Event Mesh **only where each is actually in scope**. In the current example only Cloud Integration is in scope; do not add API Management or Event Mesh simply to illustrate the product catalogue. Keep full names and exact official icons on both the group header and each included capability. Do not imply the SaaS components are separately deployed inside a BTP subaccount if their real tenant placement is unknown; show grouping as functional scope.

**External systems with Integration Suite:** Whenever Integration Suite is in scope, show a visually connected external-systems node outside the BTP global account in both outputs, with an edge to the Integration Suite capability involved. Use the actual named third-party systems and confirmed environment-specific routes if supplied; otherwise label the generic destination **`Third-party Systems`**. That generic label is an architectural endpoint category, **not** evidence that a specific system, interface, protocol, data direction, or instance count has been agreed. Do not invent any of those attributes, or add a "to confirm" annotation. Use a neutral external-system symbol rather than a misleading SAP product icon. Keep this connection distinct from the ERP/Cloud Connector path and from transport or identity flows.

Example questions to adapt to existing answers:

- "Which BTP environments need separate subaccounts: DEV, TST/QAS, and PRD, or shared DEV/TST with separate PRD?"
- "Which Integration Suite edition and capabilities are contracted? Is this project Cloud Integration only?"
- "Which ECC or S/4HANA systems and environments will connect to BTP, and which side initiates each connection?"
- "Will IAS use one shared tenant? Will IPS provision users or groups, and to which targets?"
- "Will CI/CD and Cloud Transport Management reside in a shared-services subaccount or an existing one?"

Distinguish a proposal from an as-built landscape. Do not imply that a planned service is already deployed. Keep unanswered technical details out of the client diagram rather than turning them into a list of open questions; label them only if the user explicitly requests such labels. Do not add a status legend or a "how to read this drawing" section by default.

## 3. ERP connectivity and SAP Cloud Connector

For this design, **private BTP-to-ECC or BTP-to-S/4HANA Private Cloud connections use SAP Cloud Connector**. Show the connector explicitly between each BTP connection and the correct ERP environment. Show the actual path, such as `BTP application -> Destination / Connectivity (if used) -> SAP Cloud Connector -> private SAP system`, with protocol, direction, and purpose when known; Cloud Integration flows must show their confirmed adapter and network path rather than an invented generic route. Represent each connected DEV, QAS/TST, and PRD target distinctly, including any connector mappings or separate instances actually used. Place the connector on an authorized network with reachability to the private target and its outbound secure BTP connection. Diagram labels for DEV/QAS/PRD routes do not by themselves establish the number of physical connector installations. Do not invent a single shared instance, high availability, or direct public exposure.

This is the **required connectivity pattern for these designs**, not a universal technical claim about all possible ECC or S/4HANA Private Cloud communication. Check the actual initiator and direction: SAP-initiated outbound traffic cannot be forced through a fictional Cloud Connector path. If a required private link cannot use Cloud Connector, stop and clarify that link rather than silently drawing an alternative or an impossible route. For SAP S/4HANA Public Cloud, show its own ERP node and only the agreed cloud connection and authentication; **do not** draw a Cloud Connector without a separately established reason. Do not apply the private-system rule to other SaaS products or third parties.

## 4. Build the client-facing architecture

1. Inventory the in-scope components, environments, known deployment locations, and connections. Separate shared tenants/services from services in each subaccount.
2. Represent the real hierarchy `global account -> directory -> subaccount -> subscriptions/service instances/runtimes` without creating subaccounts for visual convenience. Distinguish shared DEV/TST from isolated PRD and distinguish SaaS tenants or external systems from subaccount resources.
   Label the hierarchy explicitly in both files, including every overview and focused view: `Directory: Applications` enclosing `Subaccount: Applications DEV`, `Subaccount: Applications TST`, and `Subaccount: Applications PRD` (use domain names translated in the HTML). Name the Data, Integration, and Shared Services directories and subaccounts the same way. An environment label alone (`DEV`) is not a subaccount label.
3. Draw the client's identified ERP and every important confirmed external system and **actual connection** with source, target, initiator/direction, protocol, and business purpose where known. Distinguish end-user access, identity federation, user provisioning, private connectivity, data integration, and transport/deployment. With Integration Suite, also show a connected generic `Third-party Systems` node when specific external systems are not identified, without presenting the generic relationship as an implemented interface. A row of `BTP → Cloud Connector → ECC` text cards or a separate flow list is **not** a substitute for an architecture diagram with visually connected nodes.
4. Explain in plain language what each included directory, subaccount, and service does, why this client uses it, which environment uses it, and what it connects to. Distinguish a general product capability from a capability enabled in this project; never imply that every item in a catalog is deployed.
5. Include a compact environment summary and a visible "Proposed" or "As built" designation and revision/date. Derive counts from the rendered inventory; count any shared-services subaccount consistently. Omit unknown technical attributes; **do not add** pending-decision labels, separate "How to read this diagram", outstanding-decisions, or SAP Help Portal sections unless the user specifically asks for them.
   Place the SAP BTP global-account architecture at the **start** of the overview. Move the Microsoft Entra ID → IAS/IPS identity and shared-authentication area **after** the BTP global-account diagram, preserving the visible IAS coverage across all directories/subaccounts. Keep this reading order in the `.drawio` layout as well.

## 5. Required HTML deliverable and localization

Always write a real `.html` file, not just an HTML snippet or a textual description. **Before it, produce a real editable `.drawio` file** from the confirmed inventory, using official SAP diagram container and connector styles; validate that files open and have no broken references. Use the supplied HTML only as a reference for the responsive, navigable client presentation. The output HTML must be a self-contained UTF-8 document with inline CSS/JavaScript and embedded official SVG icons, no required CDN, API key, external font, or network request; it must open directly in a modern browser. Build the **architecture diagram as the main content**: a global-account boundary containing directory boundaries, subaccount boxes and their included services/icons; a visually separate area for SAP Cloud Connector and external systems; identity and shared services in their real placements; and rendered connector lines/arrows between actual linked components. Use the same verified node and edge map as the draw.io source. Prefer scalable SVG connectors over repeated ASCII arrows or cards; route lines without obscuring labels, and make the diagram usable on small screens by zooming/panning or reflowing to a readable stacked view. If the scenario is too dense, provide an overview and focused domain views instead of shrinking all text into illegibility. Follow SAP's documented light-blue outer area, white/blue nested boxes, grey customer-network area and thin grey-blue arrows; do not imply a connector is implemented if its flow is hypothetical.

Provide accessible navigation between domains/environments, clickable and keyboard-operable service details, a way to inspect actual connections and their protocols, mobile layout, and a legible print/PDF view. **Do not paste a large draw.io canvas into a fixed-width SVG and call horizontal scrolling or tiny scaled text "responsive".** Create a readable overview and focused domain views with responsive HTML layout; keep each service's official icon and full name legible without zoom at roughly 700px viewport width. Reflow connector diagrams or offer environment-focused views at smaller widths. Zoom/pan may supplement a usable overview, not substitute for one. The printed output must preserve the visible arrows/links. A hover-only tooltip or a list of routes detached from the architecture is insufficient. Render client-supplied names and descriptions safely as text; do not interpolate untrusted strings into `innerHTML`, script, or event-handler attributes.

Add a visible, keyboard-accessible language selector with exactly these options and language codes:

| Label | HTML `lang` |
|---|---|
| Português (Portugal) | `pt-PT` |
| English | `en` |
| Español | `es` |
| Français | `fr` |

Default to `en` unless the user chooses another language. Switching languages must update **all translatable** client-facing copy: description, diagram labels, headings, navigation, filter labels, environment descriptions, service names where translatable, service explanations, roles, connection details, status badges, accessible labels, help text, and print-visible text. The page title `CGUTECH - SAP Business Technology Platform Solution Architecture` defined in the "Presentation versus diagram" rule is fixed and is not translated in any of the four locales; keep the header, `<title>`, and `document.title` identical to it. Keep official product names unchanged where appropriate; translate surrounding descriptions accurately into all four locales (use European Portuguese, not Brazilian Portuguese). Update `<html lang>` on selection. Preserve the selected locale across a reload when browser storage is available, without requiring storage for the page to work. Never use an English fallback that produces a partly translated page: if any required translation is missing, complete it before delivery.

For service details, provide at least: official name, simple one-sentence explanation, role in this client's solution, known environments/placement, actual connections and their purpose, and proposed/as-built status; show edition when known and relevant. Avoid vague benefits, unsupported compatibility claims, sensitive credentials, internal endpoints, or personal data. When current product names, editions, feature availability, or commercial claims matter, verify against current official SAP documentation when available; omit unverified claims rather than guessing. Do not add a documentation/source-links section to the client-facing HTML by default.

## 6. Verify before delivering

- Every rendered service and connection is in scope; an uncertain technical detail is omitted rather than presented as fact or a pending label. Group BDC around Datasphere and Analytics Cloud and Integration Suite around exactly the capabilities in use: Cloud Integration-only does not turn into API Management or Event Mesh.
- Subaccount counts match the displayed hierarchy, including shared services; IAS/IPS tenant counts and DEV/TST/PRD associations match the actual answers.
- The IAS visually reaches all in-scope directories/subaccounts as the central authentication/identity source. Make clear that authorizations are enforced by BTP role collections and applications, not solely by IAS.
- Global account comes first, identity last; the diagram clearly labels every Directory and its full domain-and-environment Subaccount name. The HTML masthead, `<title>`, and `document.title` carry the exact title `CGUTECH - SAP Business Technology Platform Solution Architecture` and Cgutech's current presentation colors, while the architectural diagram retains SAP colors and connectors.
- Every service in **each HTML view and subaccount in both outputs** displays its full name immediately next to its exact official SAP asset, or an explicitly neutral fallback where there is no matching asset; this includes the overview at narrow widths. The `.drawio` file opens for editing, and its architecture agrees with the HTML. cTMS promotion shows every confirmed directory path (Application DEV -> TST -> PRD; Data and Integration DEV/TST -> PRD in the confirmed example), identifies its Shared Services placement, and does not fabricate TST Data/Integration accounts or claim unsupported artifact transports.
- Every private SAP link shows its **real** network route and correct target environment; a connector is shown when that route uses SAP Cloud Connector, without suggesting it is universal for all directions.
- The client's ECC, S/4HANA Private Cloud, or S/4HANA Public Cloud ERP is named and visibly connected in both outputs. The design routes BTP-to-ECC and BTP-to-S/4HANA Private Cloud private access via SAP Cloud Connector; S/4HANA Public Cloud has no automatic Cloud Connector. With Integration Suite, the diagram also connects its in-scope capability to named external systems or the generic `Third-party Systems` category when names are absent, without fabricating protocol, direction, or physical deployments.
- The HTML works offline, on narrow screens, by keyboard, and in print. Inspect it **visually in a browser** at desktop width and about 700px and 375px wide; if text is tiny, components are clipped, or the user must pan constantly to understand the diagram, redesign before delivering. Diagram nodes, navigation, filters, actual SVG/CSS connection lines, and connection inspection work. The language selector fully translates both initial and dynamically opened content in `pt-PT`, `en`, `es`, and `fr`; changing language also updates an open details panel.
- A client unfamiliar with BTP can understand each service, its role, and the architecture without consulting the source drawing. No unsolicited pending-decision labels, commercial-inventory, "how to read", or SAP Help Portal section appears.
